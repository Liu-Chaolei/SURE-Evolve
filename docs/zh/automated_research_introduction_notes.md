# 自动科研论文引言结构调研

调研日期：2026-09-18。论文 PDF 保存在 [`automated_research_papers/`](automated_research_papers/)；文本摘录由本地 PDF 提取，仅用于定位段落，正式引用应以 PDF 原文为准。

本次重点阅读了五篇与 SURE-Evolve 最接近的工作：The AI Scientist、The AI Scientist-v2、AI-Researcher、DeepEvolve 和 AIDE。另下载了 [Co-Scientist](automated_research_papers/ai_co_scientist.pdf) 作为生物医学方向的补充参照。

## 共同的引言骨架

这些论文的引言大多按下面的顺序推进：

1. 先把科学研究或机器学习工程描述成一个真实、连续的过程，说明问题为什么重要。
2. 回顾已有自动化方向，指出它们覆盖的是局部环节、固定搜索空间，或缺少真实执行反馈。
3. 给出一个具体缺口，通常直接对应本文要解决的系统瓶颈。
4. 用一段话把方法的关键组件与这个缺口逐一对应。
5. 提前给出验证证据，说明系统在哪些任务、基准或同行评审中接受检验。
6. 最后列出贡献，贡献内容与前文缺口一一对应。

区别在于：The AI Scientist-v2 主要写“相对于上一版修复了什么”；DeepEvolve 先放一个小实验，证明单纯进化会停滞，再引出深度调研；AIDE 则把问题抽象为代码解空间上的树搜索。它们都避免只用“我们提出一个框架”作为动机。

## 1. The AI Scientist（2024）

文件：[ai_scientist.pdf](automated_research_papers/ai_scientist.pdf)。引言从科学方法的完整流程开始：背景知识、假设、评测、证据、结论、论文和同行评审。随后指出人工研究受创造力、知识范围和时间限制，自动化一般科学发现因此长期受到关注。

第二层回顾已有自动化研究：材料和生物领域通常依赖预先限定的搜索空间；机器学习中则集中在超参数、架构或算法搜索。这些方法虽然有效，但只能覆盖科学过程的一部分，而且依赖人工设计的空间和目标。作者由此提出缺口：尚未展示无需人工参与、能够执行完整研究项目的系统。

第三层直接给出系统范围：从研究方向和初始代码出发，完成想法生成、文献搜索、实验计划、代码修改、实验迭代、论文写作和自动评审，并可将结果加入档案后继续产生下一代想法。接下来才说明技术实现，例如使用 LLM 推理、自反思和 Aider 修改代码。

贡献列表对应四类证据：端到端框架、自动论文评审、批量生成论文并展示案例、限制与伦理讨论。它的引言写法是“完整科学流程 → 现有自动化边界 → 端到端缺口 → 系统闭环 → 规模和案例证据”。

对 SURE-Evolve 的启发是：第一段可以明确语音研究实际包含文献阅读、方案提出、模型修改、训练、预测产物检查和任务评测；第二段再说明通用自动科研或 AutoML 覆盖的边界。不要一开始就列 ASR/TTS/SD 名称，而应先说明为什么语音研究的完整执行链很难自动化。

## 2. The AI Scientist-v2（2025）

文件：[ai_scientist_v2.pdf](automated_research_papers/ai_scientist_v2.pdf)。它没有重复 v1 的宏大历史，而是用很短的篇幅承接前作：v1 已经证明端到端自动科研可行，但存在两个清晰限制：依赖人工编写、按主题定制的代码模板；实验过程线性且浅，不能深入探索复杂假设。

接下来每个限制都对应一个方法改动：去除人工模板依赖，使用实验管理器和 agentic tree search 进行更深的探索；再用 VLM 反馈改进图、图注和文本解释。方法、问题和验证之间的对应关系非常紧。

引言中段立即给出外部证据：三个完全自动生成的论文被提交到 ICLR workshop，其中一个达到可接受的评审分数。作者随后承认该论文的负结果、论证不足、数据重叠和图注错误，并把这些反馈纳入后文分析。

对 SURE-Evolve 的启发是：如果论文定位为对已有系统的改进，应明确写出上一类方法的两个或三个具体瓶颈，再逐一映射到 SURE-Evolve 的设计。若没有同行评审或统一外部基准，应使用真实候选实验、失败记录和冻结测试集作为证据，不能借用“首个通过评审”等强证据表述。

## 3. AI-Researcher（2025）

文件：[ai_researcher.pdf](automated_research_papers/ai_researcher.pdf)。引言先从科学发现的认知负担和巨大解空间切入，然后把科学研究与普通工具调用区分开：研究需要跨抽象理论推理、提出新假设、持续解释意外结果，并在大量文献中保持连贯理解。

随后作者提出两个缺口。其一，现有智能体大多只能自动化检索、调度等局部任务，不能把假设、实现、实验和写作串起来；其二，缺少跨领域、可重复的自动科研评测基准。方法介绍采用三项机制回应：Resource Analyst 将概念拆成数学与代码的双向映射；Implementation Framework 用多智能体反馈反复修正；Documentation Agent 将实验产物组织成一致的论文。之后引出 Scientist-Bench，说明如何验证实现质量和文档质量。

它的引言特别重视“评价对象”的定义：系统输出同时包括代码和技术报告，二者分别接受评估。对 SURE-Evolve 来说，这提示引言应区分研究方案、候选实现、预测产物和最终论文证据，不能把“生成了一个候选”直接等同于“完成了科学发现”。

## 4. DeepEvolve（2025）

文件：[deep_evolve.pdf](automated_research_papers/deep_evolve.pdf)。它从“LLM 可以生成假设、执行代码和接受评价”开始，但马上指出更难的问题：在化学、生物和材料等开放领域，LLM 不仅要提出假设，还要把假设变成可运行的代码。

这篇引言最有特色的是先给出一个小规模观察：复现的 AlphaEvolve 在分子性质预测上经过多代迭代只获得很小提升，而且最好的算法很早出现，后续深度演化收益有限。这个观察被用来提出具体瓶颈：高质量研究想法，而不是代码变异本身，可能才是宽领域算法进化的瓶颈。

然后方法逐项回应：网络深度调研提供背景与可实现的伪代码；代码智能体支持跨文件修改；调试智能体处理执行失败；评价结果返回调研模块，形成下一轮提案。引言最后给出九个科学问题和多领域结果，形成“初步反例 → 机制设计 → 多任务验证”的结构。

对 SURE-Evolve 的启发是：可以用一个真实的语音研究观察来证明当前问题，例如候选反复停留在同一类修改、不同评分协议导致反馈不一致，或者文献方案难以落到具体模型接口。这个观察必须来自实际记录；如果没有对应实验，应只写成待验证动机。

## 5. AIDE（2025）

文件：[aide.pdf](automated_research_papers/aide.pdf)。AIDE 从机器学习工程中的试错成本开始，先回顾 AutoML、神经架构搜索和超参数优化，再指出这些方法依赖预定义配置空间，空间设计需要大量领域知识，也可能造成低效搜索和验证集过拟合。

第二段提出代码空间搜索：LLM 可以直接修改完整程序，利用其中的领域知识寻找更有希望的方案。第三段给出 AIDE 的核心抽象：把所有历史解组织成树，节点是代码和分数，边是一次改进尝试；搜索策略决定下一次从哪个节点继续，评价函数提供独立反馈。

它的引言没有声称完成完整科学发现，而是准确限定为自动化机器学习工程，并用 Kaggle、MLE-bench 和 Triton kernel 等结果说明适用范围。对 SURE-Evolve 的启发是：论文需要清楚区分“自动研究”与“候选代码优化”。SURE-Evolve 如果强调文献、研究假设和跨轮反馈，就应明确说明这些内容如何超出简单的代码树搜索。

## 对 SURE-Evolve 引言的具体建议

建议将现有引言收束为五段：

1. **研究过程与困难。** 说明语音模型研究需要把文献中的方法转化为具体结构、训练或推理改动，并通过转写文本、合成波形或时间标注获得证据。
2. **自动科研已有进展。** 简要区分端到端自动科研、代码/算法进化和 AutoML；每类只指出与本文最相关的边界。
3. **语音场景缺口。** 具体写出不同模型家族、预测产物、任务指标和计算成本使候选难以直接比较；文献知识还需要经过适用性判断才能进入模型实验。
4. **本文方法。** 用一句话给出“文献与任务约束 → 研究方案 → 候选实现 → 统一评测 → 历史反馈”的闭环，并说明 ASR、TTS、SD 是三个实例。
5. **贡献与证据。** 只列实际完成并可验证的内容：语音文献资源、候选执行接口、SURE-Eval 评测协议、真实搜索/选择/保留测试结果。若没有消融或统一效率对照，不要在引言中声称文献或反馈单独带来增益。

最值得借鉴的不是某一篇论文的“全自动”措辞，而是它们都把引言中的问题、方法组件和验证证据逐项对齐。SURE-Evolve 的引言应把区别落在已实现的语音研究链路和评测协议上，避免使用“首次结合文献和实验反馈”这类已有工作可以反驳的概括性新颖性声明。
